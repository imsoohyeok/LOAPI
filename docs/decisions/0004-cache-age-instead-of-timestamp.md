# 0004. 캐시 시각 대신 경과 시간(`ageMs`)을 보낸다

- 상태: 채택
- 날짜: 2026-10-07
- 근거: [#10 캐시 상태 배지](https://github.com/imsoohyeok/LOAPI/pull/10)
- 관련 파일: `lib/cache.ts`(`cacheMeta`), `lib/cacheStatus.ts`(`toCacheInfo`, `describeCacheStatus`), `lib/useNow.ts`, `components/CacheBadge.tsx`

## 문제

서버 캐시 때문에 사용자는 최대 5분 지난 정보를 볼 수 있습니다([0002](./0002-cache-policy-single-ttl.md)).
그래서 응답마다 "저장된 정보 · 3분 전"처럼 데이터의 출처와 나이를 보여주기로 했습니다. 나이를
계산하려면 "언제 받아온 데이터인지"를 서버가 알려줘야 합니다.

가장 단순한 방법은 서버가 받아온 시각(`fetchedAt: 12:00:00`)을 보내고, 브라우저가
`Date.now() - fetchedAt`을 계산하는 것입니다. 하지만 이 식은 **서버 시계와 브라우저 시계를 서로
뺍니다.** 사용자 PC 시계가 1분만 빨라도 방금 받은 데이터가 "1분 전"으로 보이고, 느리면 음수가
나옵니다.

## 고려한 대안

1. **서버 시각(`fetchedAt`)을 보낸다.** 위의 시계 차이(clock skew) 문제가 그대로 남습니다.
2. **서버 시각과 함께 서버의 현재 시각도 보내서 차이를 보정한다.** 결국 서버 안에서 뺄셈을 하는
   것과 같은데 필드만 늘어납니다.
3. **서버가 경과 시간(`ageMs = 서버 now - 저장 시각`)을 보내고, 브라우저가 받은 시각에서 뺀다.** (채택)

## 결정과 이유

뺄셈은 **같은 시계끼리만** 합니다.

- 서버: `ageMs = Date.now() - entry.timestamp` → 둘 다 서버 시계입니다(`cacheMeta`).
- 브라우저: `fetchedAt = 응답을 받은 시각 - ageMs` → 둘 다 브라우저 시계입니다(`toCacheInfo`).

이렇게 만든 `fetchedAt`은 브라우저 시계 기준이라, 이후 `Date.now() - fetchedAt`으로 몇 분이 지났는지
안전하게 계산할 수 있습니다. 다른 머신의 시계를 서로 빼지 않는 것은 분산 시스템에서 흔히 쓰는
원칙입니다.

부수 효과로 TanStack Query 캐시와도 잘 맞습니다. 5분 안에 같은 캐릭터를 다시 열면 요청 없이
브라우저 캐시가 쓰이는데, 나이는 저장해 둔 `fetchedAt` 기준이라 그때도 "4분 전"처럼 정확합니다.
화면에 머무는 동안 숫자가 낡지 않도록 `useNow`가 30초마다 현재 시각을 갱신합니다.

배지 문구는 처음에 "서버 캐시 / 새로 조회"였습니다. PR을 검토하면서 사용자는 "서버 캐시"라는
개발 용어를 알 필요가 없다고 보고 쉬운 말로 바꾸도록 요청해서, "저장된 정보 / 새로 불러옴"이
되었습니다(#10의 커밋 `💄 캐시 배지 문구를 쉬운 말로 변경`).

## 트레이드오프

- 네트워크 전송 시간만큼 오차가 있습니다. 브라우저는 응답이 **도착한** 시각에서 빼므로, 실제보다
  전송 시간만큼 최근으로 계산됩니다. 수백 ms 수준이고 화면은 분 단위로 내림해서 보여주므로 무시할
  수 있습니다.
- 응답 스키마에 `fromCache`, `ageMs` 필드가 추가되어 모든 프록시 라우트가 `cacheMeta()`를 붙여야
  합니다. 실제로 #12(거래소)는 #10이 머지된 뒤 `getCached`의 반환 형태가 `{ value, timestamp }`로
  바뀐 것을 반영해야 했습니다. 항목을 그대로 펼치면 타입 오류 없이 응답 형식만 깨지는 경우라서,
  다른 라우트처럼 `cached.value`와 `cacheMeta()`를 쓰도록 맞췄습니다.
- 두 필드 중 하나라도 없으면(구버전 응답 등) 배지를 그리지 않습니다. 틀린 정보보다 정보가 없는
  편이 낫다고 판단했습니다.

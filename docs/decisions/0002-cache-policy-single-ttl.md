# 0002. 서버 캐시와 클라이언트 캐시의 TTL을 한 상수로 맞춘다

- 상태: 채택
- 날짜: 2026-10-07
- 근거: [#7 React Query 도입](https://github.com/imsoohyeok/LOAPI/pull/7), [#10 캐시 상태 배지](https://github.com/imsoohyeok/LOAPI/pull/10)
- 관련 파일: `lib/cacheStatus.ts`, `lib/cache.ts`, `lib/queryClient.ts`

## 문제

캐시가 두 겹입니다.

- **서버**: API 라우트가 로스트아크 응답을 메모리(`lib/cache.ts`)에 5분 동안 저장합니다. 로스트아크
  API의 분당 요청 한도를 아끼기 위해서입니다.
- **클라이언트**: TanStack Query가 브라우저에 응답을 캐시합니다([0001](./0001-server-state-tanstack-query.md)).

두 캐시의 수명이 다르면 이상한 일이 생깁니다. 클라이언트가 1분마다 다시 요청해도 서버는 5분 동안
같은 응답을 돌려주므로 요청만 낭비됩니다. #7에서는 두 값을 같은 숫자로 맞췄지만, 각 파일이
`5 * 60 * 1000`을 따로 들고 있어서 한쪽만 바뀔 위험이 있었습니다.

## 고려한 대안

1. **각 파일에 같은 숫자를 둔다.** #7의 상태입니다. 바꿀 때 두 곳을 모두 기억해야 합니다.
2. **`lib/cache.ts`에 상수를 두고 클라이언트가 가져온다.** `lib/cache.ts`는 `import "server-only"`라서
   클라이언트 번들에서 가져오면 빌드가 실패합니다.
3. **아무 런타임에서나 읽을 수 있는 파일에 상수를 둔다.** (채택)

## 결정과 이유

`lib/cacheStatus.ts`에 `CACHE_TTL_MS`를 두고, 서버 캐시 만료와 `staleTime`이 모두 이 값을 씁니다(#10).
같은 파일에 배지 문구도 있어서 "5분 안에 검색한 적이 있어서…"라는 설명도 같은 상수로 만들어집니다.

같은 맥락에서 `lib/queryClient.ts`의 다른 기본값도 "API 한도를 아낀다"는 같은 원칙을 따릅니다(#7).

- **재시도**: 4xx(없는 캐릭터, 요청 한도 초과, 응답 형식 오류)는 다시 보내도 결과가 같거나 한도만
  더 소모하므로 재시도하지 않습니다. 네트워크 오류와 5xx만 한 번 더 시도합니다(`shouldRetry`).
- **`refetchOnWindowFocus: false`**: 캐릭터 정보는 몇 분 사이에 바뀌지 않는데, 탭을 오갈 때마다
  다시 요청하면 분당 한도만 깎입니다.

## 트레이드오프

- 사용자는 최대 5분 지난 정보를 볼 수 있습니다. 그래서 #10에서 "저장된 정보 · 3분 전" 배지로
  데이터의 나이를 화면에 드러냈습니다([0004](./0004-cache-age-instead-of-timestamp.md)).
- 서버 캐시는 프로세스 메모리라서, 서버리스 환경에서는 인스턴스마다 따로입니다. 같은 캐릭터라도
  요청이 다른 인스턴스로 가면 다시 조회됩니다. 공유 캐시(예: Redis)가 필요해지면 `lib/cache.ts`의
  `getCached`/`setCached` 인터페이스 뒤에서 바꿀 수 있습니다.

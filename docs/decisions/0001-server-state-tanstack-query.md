# 0001. 서버 상태는 TanStack Query로 관리하고 전역 스토어는 미룬다

- 상태: 채택
- 날짜: 2026-10-07
- 근거: [#7 React Query 도입 및 검색 훅 전환](https://github.com/imsoohyeok/LOAPI/pull/7)
- 관련 파일: `lib/api.ts`, `lib/queryClient.ts`, `app/providers.tsx`, `lib/useCharacterSearch.ts`, `lib/useRoster.ts`

## 문제

이 앱이 다루는 상태는 대부분 캐릭터·원정대처럼 **로스트아크 API에서 오는 서버 상태**입니다.
#7 이전에는 `useCharacterSearch`, `useRoster`가 로딩·에러·요청 취소를 각자 `useState`와
`useEffect`로 처리했습니다. 그 결과 두 훅의 품질이 달랐습니다.

- `useRoster`(#4)는 `AbortController`로 이전 요청을 취소해서, 늦게 도착한 응답이 최신 결과를
  덮어쓰지 않았습니다.
- `useCharacterSearch`에는 같은 처리가 없어서, 캐릭터를 연달아 검색하면 이전 응답이 최신 결과를
  덮어쓰는 **응답 경합 버그**가 있었습니다. 원정대 작업 중에 발견했습니다.

같은 문제를 훅마다 손으로 풀면 빠뜨리는 곳이 반드시 생긴다는 것이 이 버그로 드러났습니다.

## 고려한 대안

1. **기존 훅에 `AbortController`를 똑같이 추가한다.** 버그는 고쳐지지만 캐시, 중복 요청 합치기,
   재시도 정책을 훅마다 다시 만들어야 합니다.
2. **Zustand 또는 Jotai를 도입한다.** 둘 다 클라이언트 상태를 위한 도구라서 요청 취소·캐시 만료·
   재시도 같은 서버 상태 문제를 직접 풀어 주지 않습니다. 당시 클라이언트 상태는 트래커의
   localStorage 기록과 입력창 값 정도였고, 공유가 필요한 값(비교 대상 캐릭터)은 URL에 두기로
   했습니다([0003](./0003-url-as-source-of-truth.md)).
3. **TanStack Query(v5)를 도입한다.** (채택)

## 결정과 이유

서버 상태는 TanStack Query로 옮기고, 전역 클라이언트 스토어는 여러 페이지가 함께 쓰는 클라이언트
상태가 실제로 생길 때까지 미룹니다.

- **경합이 구조적으로 사라집니다.** 화면에 보이는 값은 항상 "현재 쿼리 키의 캐시"입니다. 검색어가
  바뀌면 쿼리 키가 바뀌므로 이전 키의 응답이 늦게 와도 화면에 반영될 자리가 없습니다. `queryFn`이
  받는 `signal`을 `fetch`에 넘겨서 더 이상 보지 않는 요청은 취소까지 합니다.
- **페이지 간 캐시를 공유합니다.** `lib/api.ts`의 `queryKeys` 팩토리 한곳에서 키를 만들어서, 비교·
  트래커·원정대가 같은 캐릭터를 조회하면 같은 캐시를 씁니다.
- **기존 호출부를 바꾸지 않았습니다.** `useCharacterSearch`의 반환 형태(`data`, `loading`, `error`,
  `search`, `reset`)를 유지해서 페이지 코드는 그대로입니다.
- **증명했습니다.** 응답 순서를 직접 제어하는 fetch 목으로 경합을 재현하는 테스트를 만들고, 같은
  테스트를 기존 훅에 돌리면 `"이전캐릭"`이 `"최신캐릭"`을 덮어써서 실패하는 것을 확인했습니다.

`QueryClient`는 `app/providers.tsx`에서 `useState(makeQueryClient)`로 만듭니다. 모듈 최상단에서
만들면 서버에서 여러 사용자의 요청이 같은 캐시를 공유하게 되기 때문입니다.

나중에 즐겨찾기처럼 여러 페이지가 함께 쓰는 클라이언트 상태가 생기면, `persist` 미들웨어로
localStorage를 대체할 수 있는 Zustand를 먼저 검토합니다.

## 트레이드오프

- 의존성이 하나 늘었습니다. 다만 직접 짠 로딩·취소·재시도 코드가 그만큼 줄었습니다.
- `search()`가 더 이상 Promise를 반환하지 않습니다. 반환값을 쓰던 곳이 없어서 영향은 없었지만,
  "검색이 끝난 뒤 무엇을 한다"는 흐름은 이제 쿼리 상태(`isSuccess` 등)로 표현해야 합니다.
- 캐시 정책(`staleTime`, 재시도)이 전역 기본값으로 모였습니다. 정책을 한곳에서 설명할 수 있는
  대신, 쿼리마다 다른 정책이 필요하면 개별 옵션으로 덮어써야 합니다. 거래소 카테고리 목록의
  `staleTime: Infinity`(#12)가 그 예입니다.
